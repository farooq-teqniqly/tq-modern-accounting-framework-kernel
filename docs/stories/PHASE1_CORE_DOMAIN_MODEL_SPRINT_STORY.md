## Story Summary

**As a** system architect and developer  
**I want** to implement the pure domain model for the Accounting Kernel in a standalone assembly  
**So that** we have a host and infrastructure-agnostic foundation that can be used with any hosting model and persistence technology

**Reference**: [Technical Proposal: Modern Accounting Framework Kernel](./Technical_Proposal.md) - Phase 1 (Weeks 1-4)

---

## Problem Statement

- Need a reusable accounting kernel that abstracts core accounting concepts (accounts, transactions, attributes)
- Domain logic must be completely independent of infrastructure and hosting concerns
- Foundation required before building event sourcing, CQRS, and other infrastructure layers
- Domain model must support both personal finance and business accounting use cases
- Need to establish patterns for aggregates, value objects, and domain events

---

## Solution Overview

1. Create standalone `AccountingKernel.Domain` assembly with zero external dependencies
2. Implement core aggregates: `Account`, `AccountType`, `TransactionMapping`
3. Implement `TransactionEntry` entity (within Account aggregate)
4. Define value objects: `AttributeDefinition`, `TransactionDate`, `FieldName`, `AttributeName`
5. Create domain service interfaces (implementations in Infrastructure layer)
6. Establish domain events for all state changes
7. Create unit test project `AccountingKernel.Domain.Tests` with comprehensive domain logic tests

---

## Technical Approach

- **Pure Domain Model**: No dependencies on EF Core, Dapper, ASP.NET Core, or any infrastructure
- **ID Generation**: Base classes (`AggregateRoot` and `Entity`) automatically generate IDs using `Guid.CreateVersion7()` in their constructors
- **Factory Methods**: All aggregates expose static `Create()` methods for validation and invariant enforcement (ID generation handled by base class)
- **Aggregate Roots**: `Account`, `AccountType`, `TransactionMapping` as aggregate roots
- **Domain Events**: Emit domain events for all state changes (e.g., `TransactionPosted`, `AttributeAdded`)
- **Value Objects**: Immutable records for domain concepts (dates, names, definitions)
- **Domain Service Interfaces**: Define interfaces only (e.g., `IPostingService`, `IAttributeCalculator`)
- **Testing**: xUnit with built-in assertions, NSubstitute for mocks (no infrastructure setup required)

## Notes

### Important Implementation Considerations

1. **ID Generation**: 
   - Base classes (`AggregateRoot` and `Entity`) automatically generate IDs using `Guid.CreateVersion7()` in their constructors
   - Never use `Guid.NewGuid()` or allow external ID assignment in factory methods
   - For loading from persistence, use the protected constructor with `Guid id` parameter

2. **Aggregate Boundaries**: 
   - `TransactionEntry` is an entity within the `Account` aggregate (not a separate aggregate)
   - `Account`, `AccountType`, and `TransactionMapping` are separate aggregate roots

3. **Domain Events**: 
   - Events should be immutable
   - Include aggregate ID and relevant data
   - Events are raised but not persisted in this phase (persistence happens in Phase 2)

4. **Value Object Validation**: 
   - Consider adding validation to value object constructors (e.g., `AccountName` should not be empty)
   - Keep validation simple in domain layer (detailed validation in Application layer)

5. **Factory Methods**: 
   - All aggregates should have static `Create()` methods
   - Factory methods enforce invariants and validation
   - ID generation is automatic (handled by base class constructor)
   - Use private constructors to force use of factory methods
   - Private constructor with `Guid id` parameter needed for persistence loading (Phase 2)

6. **Domain Service Interfaces**: 
   - Keep interfaces focused on domain concepts
   - Avoid infrastructure concerns (e.g., don't include `DbContext` or `IDbConnection`)
   - Interfaces will be implemented in Infrastructure layer (Phase 2-3)

7. **Testing Strategy**: 
   - Test base classes generate IDs correctly using `Guid.CreateVersion7()`
   - Test base class domain events collection (for `AggregateRoot`)
   - Test aggregate invariants
   - Test factory methods validate correctly (ID generation is automatic)
   - Test domain events are emitted correctly
   - Test value object immutability
   - Test persistence constructors (with `Guid id`) work correctly
   - No need to test infrastructure concerns (that's Phase 2)

### Architectural Decisions

- **Base Classes with ID Generation**: `AggregateRoot` and `Entity` base classes are implemented with automatic ID generation:
  - Parameterless constructor generates ID via `Guid.CreateVersion7()`
  - Protected constructor with `Guid id` parameter for loading from persistence
  - This ensures consistent ID generation across all aggregates/entities
- **Domain Events Collection**: `AggregateRoot` base class provides domain events collection:
  - `IReadOnlyCollection<IDomainEvent> DomainEvents` property
  - `AddDomainEvent()` protected method
  - `ClearDomainEvents()` public method
- **Factory Methods**: Factory methods (e.g., `Account.Create()`) focus on:
  - Business invariant validation
  - Property initialization
  - ID generation is automatic (handled by base class constructor)
- **Constructor Visibility**: Aggregate/entity constructors are private to enforce factory method usage:
  - Private parameterless constructor for factory methods
  - Private constructor with `Guid id` for persistence loading (used by Infrastructure layer in Phase 2)
- **ExternalTransaction Type**: The `ExternalTransaction` type referenced in `IPostingService` should be defined in the Domain layer as a value object or simple class (not an aggregate).

### Non-Obvious Constraints

- Domain assembly must target .NET Standard 2.1 or .NET 8+ (to support `Guid.CreateVersion7()`)
- All public APIs should be designed for extension (sealed classes only if there's a specific reason)
- Consider making aggregate constructors internal or protected to enforce factory method usage
- Domain events should be simple data containers (DTOs), not complex objects
